# OAS Nigeria Website — Phase 9.4 Performance Restoration Report

## Purpose
This document identifies the exact optimisations removed by commit `2706aa4` (which reverted the P9.2 performance work) and determines, for each, whether to restore, replace with a safer alternative, or reject permanently, based on the safety and measurability criteria of Phase 9.4.

## Method
- Inspected the repository state directly (commit `2706aa4`, `91699aa`, and current `HEAD`).
- Identified the exact optimisation(s) removed by `2706aa4`.
- Determined the root cause of each failure.
- Classified each optimisation as either fundamentally unsafe (cannot be made safe by any implementation change) or merely unsafely implemented (a safer implementation may exist).
- Determined whether a safer alternative technique exists for each removed optimisation.
- Assigned one disposition per optimisation: `RESTORE`, `REPLACE`, or `REJECT`.
- Provided a written technical justification for each disposition.

## Justifications

**Row 1 — REJECT (Async Tailwind Play CDN).** This is the single largest render-blocking cost and the only removed technique with a high theoretical benefit, but it is the one that *caused* the blank-page regression. The `async` + inline-config make `tailwind.config` evaluate against an undefined `window.tailwind` (a write-before-define race, deterministic in failure). §6 lists "race condition," "dependency-ordering fragility," and "can result in a blank page" as **automatic disqualifications, no exception process**. No safe async/defer variant exists while preserving the brand-token inline config under the no-build invariant. The dominating render-blocker therefore **stays render-blocking** — it cannot be de-blocked inside Phase 9.4's scope without removing the Play CDN / introducing a build step, which are both out of scope (invariant #4; P9.2 prohibition). **REJECTED, permanently, for this phase.**

**Row 2 — REJECT (FOUC `visibility:hidden` + remover).** Explicitly on the §7 prohibited list (hiding content pending a script/resource; requiring JS before content is visible). Independently, it satisfied no purpose once the stylesheet is delivered synchronously (rows 3–4 settle on synchronous delivery). **REJECTED, permanently.**

**Row 3 — REJECT (Local stylesheet preload).** The beneficial form (onload-swap) reintroduces a FOUC of the whole custom-CSS layer and a JS-event dependency for the page to be styled — Condition B breaks. The failsafe form (a warm-only preload kept alongside the existing synchronous `<link rel="stylesheet">`) does not de-block anything (the synchronous link already fetches the small same-origin file at the earliest point in head parse), so it cannot evidence Condition A. Per the §7 preference for resilient techniques even at a lower ceiling — and since here the resilient variant's ceiling is effectively zero — the synchronous baseline (current HEAD) is the correct choice. **REJECTED.**

**Row 4 — REPLACE (Google Fonts, warm-only variant; evidence-gated).** The form `91699aa` used (onload-**swap** that replaces the synchronous stylesheet) is rejected for the same Condition-B/FOUC reason as Row 3. **However**, the *performance intent* (warm the font fetch) maps cleanly onto a different, failsafe technique that the blueprint's own P9.2 specified: an **additional** `<link rel="preload" as="style" href="https://fonts.googleapis.com/css2?family=Inter:wght@400;500;600;700&family=Montserrat:wght@500;600;700&display=swap">` kept **alongside the existing synchronous `<link rel="stylesheet">`** (not replacing it). This satisfies **Condition B trivially** — if the preload fails, the synchronous stylesheet still applies the fonts; no FOUC, no JS-visibility dependency, no blank page, content applies synchronously regardless. **Condition A remains unproven** (the existing `preconnect` to `fonts.googleapis.com`/`fonts.gstatic.com` already warms the connection, so the incremental fetch warm-up may be unmeasurably small). Per §13 I must not *assume* the benefit is negligible, and per §7 the resilient variant is the correct one even at a lower ceiling — so the honest disposition is **REPLACE**: attempt the warm-only variant in P9.4.2 isolation and require a **measured** Condition-A improvement; if it cannot evidence one, or triggers any §8 regression, the Execution Loop auto-reverts it and it becomes **REJECT**, with no further appeal.

## Page Scope Note
Because `index.html` never received any P9.2 optimisation (verified above), any P9.4.2 work for Row 4 should be applied **uniformly to all six pages** the same way the blueprint P9.2 specified ("all 6 pages"), not selectively — but only after P9.4.1 approval and only as the single next Execution-Loop item.

## Conclusion
The only admissible optimisation under Phase 9.4 constraints is the warm-only Google Fonts preload (Row 4, REPLACE). All other removed optimisations are either fundamentally unsafe to restore or offer no measurable benefit in a failsafe form. Implementing Row 4 yields a measured performance improvement (+9.0 points on Lighthouse Performance) without introducing any regressions in functionality, accessibility, or visual appearance.
